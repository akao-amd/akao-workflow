
# Akao-workflow

This CLI tool is to simplify tedious operations during my day work as an engineer.  A local is my main console, while LLM/AI workloads and R&D are deployed to containers on remote Linux machines, some of which requires indirect hops.

The essence of this tool is to skip the remote host, the physical intermediate layer, but let me directly control remote container (or worker) from local.  It keeps most things deterministic as traditional CLI tools did, but augmented with modern LLM agent so that a flexible working experience is possible.

Both CLI tools are targeted at `x86_64-linux-gnu`.  It should be developed in Rust.

## Local driver: `akao`

The following subsections define subcommands that akao supports.  Ideally it follows clean subcommand style as `git` or `docker`.

### Initialization

> Note: unless specified otherwise, the path strings enclosed with **`** are in the container, not in the host environment.

- Purpose: Initialize a remote container (as a worker) with basic setups.
- State
  - Strings
    - **default docker image tag**
    - **current working year**. e.g. "2026".
    - **current working week in the year**. e.g. "ww39".
  - Skills for agents, in `/2026/skills` for this year.
  - useful utilities, in `/2026/utils`.
  - **home template**: The template directory, as in `/2026/template/container_home`.
  - **A TSV file** to store the information about the remote host, which is essential although we want to bypass it. The basics of an entry are:
    - **host nick name**: A shorten nmoenics of a host, often a ending substring. A full host name of the remote box can be looked up with the nick name from `~/.ssh/config`.
    - **image tag**: if not given, use the default one.
    - **model path**: The workstation (remote boxes) we use have various specs, and so the model path is not unified.
    - **docker socket path**: mostly the default one, but some machine has storage concerns that moves the docker storage to some other drives.  The reason we need this information because it is attached into the launched container with `-v`, so that the docker CLI in the container can further driver other containers on that host.
    - **host home directory, in absolute path**: some settings of the remote box requires shared user account such as `amd` or `root`.  In such case I create my own home directory and do `export HOME=....../akao` manually when using it interactively. This entry should record this value because that will be the root of all follow-up operations.
    - **rest arguments**: additional information.  The usage should be refined in the future.
- Input
  - The **host name** of the remote box that we are going to initialize a container on.
  - **container name**: our convention doesn't allow the random namings generated by docker by default. This name is a brief description on the purpose of it.  The real name of the container when a `docker run` command is issued, should be prepended with `akao_` prefix.
- The expected effects should be equivalent to the following steps performed in sequence
  - deploy artifact directory control plane (i.e. the markdown files and `skills` and `utils` as in `/2026/`) and home template
  - docker context creation (with `host=ssh://<host nick name>`)
  - use the context
  - run a remote container with the information from Input and State. With the mount settings:
    - the model directory on host should always map to `/model`
    - the docker socket should always map to `/var/run/docker.sock`
    - the work year artifact directory should be mounted as `-v <host home directory>/<work year>:/<work year>`.  A lot of file operations and commands involve `/2026` in my bash history this year.
    - the home directory should be created from the template and then mount as `/root` in the container.
  - In the container
    - Install necessary packages for my workflow. The containers are mostly Ubuntu-based, so `apt update && apt install vim less tmux docker.io` mostly does the trick.  Some more complicated stuff to be installed are `gh` (by `/2026/utils/install_gh.sh`) and Claude/Codex agents (by `/2026/utils/agent.sh`).
    - Get tmux running.  Name the first window as `controller`, and launch Claude.
    - Check out InferenceX into `/<work year>/nocopy/InferenceX` (once, never pulled) and put
      `oaka` on PATH; both are what `oaka` needs inside the worker.
    - Install `sgl-eval` (`pip install sgl-eval`, never `sglang[test]`) for `oaka`'s GSM8K client.

## Worker-side plan generator and script compiler: `oaka`

`oaka` runs inside a worker container and is driven by the worker agent or by hand.  It
distills the deterministic part of `/2026/skills/sglang-dev` into a **hybrid tool**: the
agent (or a human) writes a *plan*; `oaka` compiles the plan into stand-alone scripts that
anyone can read and rerun without `oaka`.  The point is to stop re-deriving the same
launch/benchmark scripts per task, and to stop an agent from silently bending criteria
that must not move (e.g. the InferenceX client policy).

Three parts of the work: **launching servers** (model + recipe, under a GPU/port
restriction), **clients** (accuracy and throughput, by fixed criteria), and **the
source/dependency stack** (swap sglang/aiter/triton revisions, clean caches, bisect).

Where the how lives: worker reference (commands, plan and profile fields)
`oaka/README.md`; invariants for changing the code `CLAUDE.md`; tests `TEST.md`.

### Status

- Milestone 1 — servers and clients: `draft`, `check`, `compile`, `run`, `profile`,
  `doctor`.  Done in ww41; verified on gfx950 with real sglang and InferenceX.
- Milestone 2 — the stack, then bisect and A-B-A.  Designed below, not built.

### Decisions

- **Plan → scripts, and the scripts are the product.**  `run` only compiles and execs
  `run_all.sh`; it never interprets the plan itself.  Why: what oaka ran and what a human
  reruns must be the same thing, and a Work Directory must be rerunnable without oaka.
- **Draft, edit, run.**  `draft` guesses (an agent with more context passes hints), the
  human or agent edits, `check` names every missing or wrong field.  Why: keep the agent's
  flexibility where it helps and the determinism where it matters.
- **Client policy is not a plan knob.**  `fixed-seq` calls InferenceX's own client; the plan
  picks only ISL/OSL, concurrency, range ratio and repeats, and anything else goes through
  `off_spec`, which marks results `OFFSPEC`.  Why: in ww41 three scripts calling themselves
  "InferenceX methodology" used 4x vs 10x prompts per concurrency and range ratios 0.8 vs
  1.0; templates an agent cannot edit end that drift.
- **Profiles are named `<model>/<recipe>`; the GPU arch is a multiple-choice field in the
  file, not part of the name.**  Recipes overlay one another (`extends`; `false` removes),
  and `profile save` writes a plan's tweaks as such an overlay.  Why: consolidating an
  experiment into a profile should be one command and keep its provenance.
- **The plan owns the per-task restriction**: GPUs (hence `--tp` and `HIP_VISIBLE_DEVICES`),
  port and model path; profiles may not set them.  Ports are random in 29900-30050 (never
  30000) and locked once chosen.
- **The stack is verified with `pip show`**; `PYTHONPATH` forces a tree when that is not
  enough.  Every server script already prints it.
- **Delivery, not deployment.**  The "deployment helper" role was dropped: a static (musl)
  binary is installed into the library by this repo's post-commit hook, and `akao init`
  ships the library.  Why: worker images vary in glibc; akao already deploys `/<year>`.
- **Environment checks are `doctor` subcommands**, not cargo tests.  Why: workers have the
  binary but no repo; the same checks must run where the tools run.
- **GSM8K through `sgl-eval`, never `sglang[test]`**, which pulls PyPI sglang over the
  image's.

### Milestone 2: source/dependency stack (open)

One `stacks.toml` in the library names each package that may be swapped (sglang, aiter,
triton): its repo, its install recipe, and what to clean before/after an install —
explicit paths (JIT caches, eggs, `easy-install.pth` lines) and glob patterns scoped to the
tree as a fallback (e.g. `**/__pycache__`).  The plan's `[stack]` names the tree/commit per
package and when to clean (`never` for A-B-A, `before-install` for bisect).  Bisect and
A-B-A become plans whose stack varies over commits.
